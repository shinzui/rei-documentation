Rei uses two configuration sources:

1. **YAML config file** — User preferences (workspace path, editor, display settings)
2. **Environment variables** — Infrastructure settings (database, LLM provider/transport/model, observability)

## Config File

### Loading Order

Rei checks for a config file in priority order (first found wins):

| Priority | Location | Description |
|----------|----------|-------------|
| 1 | `$REI_CONFIG` | Custom path via environment variable |
| 2 | `./rei.yaml` | Local config in current directory |
| 3 | `~/.config/rei/config.yaml` | XDG standard location |
| 4 | `~/.rei/config.yaml` | Legacy fallback |

If no config file is found, defaults are used.

### Default Values

| Setting | Default | Description |
|---------|---------|-------------|
| `workspace.path` | `~/rei-workspace` | Where markdown files are stored |
| `display.color` | `auto` | Color output: `auto`, `always`, `never` |
| `display.date_format` | `%Y-%m-%d` | Date format (strftime) |
| `display.time_format` | `%H:%M` | Time format (strftime) |
| `editor` | None | Falls back to `$EDITOR` env var |
| `git.enabled` | `true` | Master switch for git integration |
| `git.commit_notes` | `true` | Auto-commit note changes |
| `git.commit_reflections` | `false` | Auto-commit reflection changes |
| `git.commit_docs` | `false` | Auto-commit attached documents |
| `git.commit_guidance` | `false` | Auto-commit guidance prompt changes |
| `git.include_tags_in_message` | `true` | Include note tags in commit body |
| `git.include_actor_in_message` | `true` | Include actor in commit body |
| `git.cache_expiry_hours` | `24` | Hours to cache git repo detection |

### Example Config File

Save as `~/.config/rei/config.yaml` (global) or `./rei.yaml` (local):

```yaml title="~/.config/rei/config.yaml"
workspace:
  path: ~/rei-workspace

editor: nvim

display:
  color: auto
  date_format: "%Y-%m-%d"
  time_format: "%H:%M"

git:
  enabled: true
  commit_notes: true
  commit_reflections: true
  commit_docs: true
  commit_guidance: true
```

<Callout type="info">
The `~` prefix is expanded to your home directory.
</Callout>

The local config (`./rei.yaml`) is useful for project-specific settings that override your global configuration.

## Aliases

Define short command aliases in your config file, similar to git aliases. Each alias maps a short name to a full command with arguments.

```yaml title="rei.yaml"
aliases:
  tw: today -c work --actions --habits
  i: intention
  sh: intention show --full
  ls: intention list --active
  h: habit
```

With the above config, `rei tw` expands to `rei today -c work --actions --habits`. Additional arguments are appended, so `rei tw --verbose` becomes `rei today -c work --no-intentions --verbose`.

**Rules:**
- Built-in commands take precedence — an alias cannot shadow a built-in command name (e.g., `today`, `intention`)
- No recursive expansion — aliases are expanded once, not recursively
- First argument only — only the first CLI argument is checked for alias matches

**Listing aliases:**

```bash
rei alias list    # Show all configured aliases
rei alias         # Same as above (list is the default)
```

## Dashboard Panels

Configure custom intention query panels that appear in the `rei today` command output. Each panel runs an independent query against the read model.

```yaml title="rei.yaml"
dashboard:
  panels:
    - label: "Kanban Board"
      where: "workflow:exists"
      group_by: "workflow"

    - label: "In Development"
      where: "version-phase=development"
      context: "work"

    - label: "Queue"
      state_tag: "queue"
      category: "projects"
```

| Field | Required | Description |
|-------|----------|-------------|
| `label` | Yes | Display name shown as the panel header |
| `where` | No | Property filter expression (same syntax as `intention list --where`) |
| `state_tag` | No | Filter by state machine system tag: `queue`, `active`, `done`, `terminal` |
| `group_by` | No | Property key to group results by (sorted by state machine order when applicable) |
| `context` | No | Limit to intentions within this context (cannot combine with `category`) |
| `category` | No | Limit to intentions within this category slug (cannot combine with `context`) |

For full details and examples, see the [Dashboard Panels Guide](/docs/guides/dashboard).

## Environment Variables

### Required: Database

Rei stores events in PostgreSQL through the kiroku/keiro event store.

| Variable | Description | Required |
|----------|-------------|----------|
| `REI_PG_CONNECTION_STRING` | Rei-specific database connection string | Recommended |
| `PG_CONNECTION_STRING` | Database connection string (fallback) | Yes (if `REI_PG_CONNECTION_STRING` not set) |

Rei checks `REI_PG_CONNECTION_STRING` first, then falls back to `PG_CONNECTION_STRING`. Using the Rei-specific variable avoids conflicts when Rei is installed globally alongside other applications.

```bash
# Recommended: Rei-specific variable (won't conflict with other apps)
export REI_PG_CONNECTION_STRING="host=localhost port=5432 dbname=rei user=postgres"

# Also works: generic variable (used as fallback)
export PG_CONNECTION_STRING="host=localhost port=5432 dbname=rei user=postgres"
```

### Optional: AI Agent

Rei's LLM access is **provider-neutral and configurable** by provider, transport, and model. It is built on the in-house **baikai** library, which speaks to Anthropic, OpenAI, and the `claude -p` / `codex exec` command-line tools. You can configure it two ways — **environment variables** or an **`llm:` section in the YAML config file** (per-project or global). Environment variables take precedence over the file.

<Callout type="info">
**Precedence:** `REI_LLM_*` environment variables **>** the `llm:` section of your config file **>** the built-in default (Anthropic + CLI). Within the file layer, a project `./rei.yaml` overrides the global `~/.config/rei/config.yaml`.
</Callout>

#### Environment Variables

| Variable | Description | Default |
|----------|-------------|---------|
| `REI_LLM_PROVIDER` | `anthropic` or `openai` | `anthropic` |
| `REI_LLM_TRANSPORT` | `cli` (subscription, no key) or `api` (per-token, needs a key) | `cli` |
| `REI_LLM_MODEL` | Model id forwarded to the provider/CLI (e.g. `sonnet`, `gpt-5-codex`) | provider/CLI default |
| `REI_LLM_API_KEY` | Explicit API key for the `api` transport | - |
| `ANTHROPIC_API_KEY` | Anthropic key, read by baikai when `REI_LLM_API_KEY` is unset | - |
| `OPENAI_API_KEY` | OpenAI key, read by baikai when `REI_LLM_API_KEY` is unset | - |

#### Provider / Transport Options

The default — `anthropic` + `cli` — preserves the original behavior exactly: it calls the local `claude -p` CLI, billed against your Claude subscription, with **no API key**.

**CLI transport vs API transport.** The `cli` transport runs the vendor's command-line tool (`claude -p` for Anthropic, `codex exec` for OpenAI), so it is billed against your **subscription**, needs no API key, and reports **zero token usage**. The `api` transport calls the vendor's HTTP API (Anthropic Messages / OpenAI Chat Completions), so it is **billed per token** and **requires an API key**.

```bash
# Default: Anthropic over the claude -p CLI (subscription, no key)
# (nothing to set)

# Anthropic Messages API with an explicit model
export REI_LLM_TRANSPORT=api
export ANTHROPIC_API_KEY=sk-ant-...
export REI_LLM_MODEL=sonnet

# OpenAI Chat Completions API
export REI_LLM_PROVIDER=openai
export REI_LLM_TRANSPORT=api
export OPENAI_API_KEY=sk-...
export REI_LLM_MODEL=gpt-5

# OpenAI over the codex exec CLI (subscription)
export REI_LLM_PROVIDER=openai
export REI_LLM_TRANSPORT=cli
```

#### YAML Config File (`llm:` section)

Instead of (or in addition to) environment variables, set the provider/model in the config file so it sticks per-project or globally without exporting variables. The file is resolved in this order: `$REI_CONFIG` → `./rei.yaml` (**project**) → `~/.config/rei/config.yaml` (**global**) → `~/.rei/config.yaml`. Add an `llm:` section:

```yaml title="./rei.yaml (project-local) or ~/.config/rei/config.yaml (global)"
llm:
  provider: openai      # anthropic | openai   (optional)
  transport: api        # cli | api            (optional)
  model: gpt-5-codex    # model id             (optional)
  # api_key: sk-...     # discouraged in a committed file — prefer the env key below
```

Every field is optional; an omitted field falls back to the env var, then the built-in default. **Prefer the environment** (`ANTHROPIC_API_KEY` / `OPENAI_API_KEY`) for the API key rather than committing `api_key` to a shared/checked-in file. A typical split is a global `~/.config/rei/config.yaml` choosing your usual provider/model, with a project `./rei.yaml` overriding it for a specific repo, and `REI_LLM_*` for one-off overrides in a shell.

**Legacy compatibility.** The old `REI_LLM_BACKEND` variable is still honored when `REI_LLM_PROVIDER` and `REI_LLM_TRANSPORT` are both unset: `claude-cli` maps to Anthropic + CLI and `anthropic-api` maps to Anthropic + API (with the key taken from `REI_LLM_API_KEY`, else the legacy `REI_ANTHROPIC_API_KEY`). Prefer the new variables.

### Optional: Connection Pool

| Variable | Description | Default |
|----------|-------------|---------|
| `PG_POOL_SIZE` | Connection pool size | 10 |
| `PG_POOL_TIMEOUT` | Pool acquisition timeout (seconds) | 10 |
| `PG_POOL_MAX_CONNECTION_IDLE_TIME` | Max idle time (seconds) | 600 |
| `PG_POOL_MAX_CONNECTION_LIFETIME` | Max connection lifetime (seconds) | 1800 |

### Optional: Observability

Rei is instrumented with OpenTelemetry tracing. **The SDK is disabled by default** — no spans are exported unless you explicitly opt in. Telemetry turns on automatically when you point Rei at an OTLP collector (set `OTEL_EXPORTER_OTLP_ENDPOINT`, `OTEL_EXPORTER_OTLP_TRACES_ENDPOINT`, or a non-empty `OTEL_TRACES_EXPORTER`), or explicitly via `REI_TELEMETRY_ENABLED=true`.

| Variable | Description | Default |
|----------|-------------|---------|
| `REI_TELEMETRY_ENABLED` | Enable Rei telemetry when `true` | unset (off) |
| `OTEL_SDK_DISABLED` | Disable the OpenTelemetry SDK when `true` (overrides auto-enable) | unset |
| `OTEL_TRACES_EXPORTER` | OpenTelemetry traces exporter (a non-empty, non-`none` value enables telemetry) | unset |
| `OTEL_EXPORTER_OTLP_ENDPOINT` | OTLP collector endpoint (enables telemetry when set) | unset |
| `OTEL_EXPORTER_OTLP_TRACES_ENDPOINT` | OTLP traces-specific endpoint (enables telemetry when set) | unset |
| `OTEL_SERVICE_NAME` | `service.name` reported in spans | `rei` |
| `REI_DEPLOYMENT_ENVIRONMENT` | `deployment.environment` reported in spans | unset |

```bash
# Export traces to a local collector (e.g. Jaeger)
export OTEL_EXPORTER_OTLP_ENDPOINT="http://localhost:4318"
export REI_DEPLOYMENT_ENVIRONMENT=dev
```

The `rei worker kiroku` process additionally exposes a kiroku-metrics HTTP server for live subscription status. See the [Observability](/docs/observability) page for the full span families, metrics guidance, and collector setup.

## Complete Example

```bash title=".envrc"
# Database (required)
export REI_PG_CONNECTION_STRING="host=localhost port=5432 dbname=rei user=postgres"

# AI (optional - defaults to Anthropic over the claude -p CLI, no key)
export REI_LLM_TRANSPORT=api
export ANTHROPIC_API_KEY=sk-ant-your-key-here

# Pool tuning (optional)
export PG_POOL_SIZE=20

# Editor fallback (if not set in config.yaml)
export EDITOR=vim
```
